# 旧版执行器迁移修复

2026-10-04。用户在 macOS 发布应用点击“迁移”没有反馈；本轮排查与修复针对旧 LaunchAgent 向桌面应用托管方式的迁移。

## 原因

原按钮先调用 `window.confirm`，只有返回 `true` 才执行 `migrate_legacy`。当前依赖 Wry 0.57.0 的 macOS `WKUIDelegate` 没有实现 JavaScript confirm 处理；WebKit 默认将其当作取消。真实发布应用中点击后没有对话框或状态变化，旧服务仍在运行，桌面数据目录也没有迁移产物。

另外，旧流程只迁连接凭据，不复制任务去重记录和目录同步状态。新版使用另一个数据目录，既看不到历史任务，也无法靠原任务编号拦住重复请求。迁移必须保留这些状态，不能只让连接状态变绿。

## 修复内容

- 使用应用内确认弹窗，显示忙碌、失败原因、备份位置及成功后的“启动并连接”；取消不执行迁移。
- 命令已成功、仅状态刷新失败时，保留成功结果，避免诱导用户重新执行迁移。
- 迁移前检查配置和任务状态；复制任务、去重记录、同步状态及已有安全设置，保留原数据目录。
- 后端配置复制到桌面应用自己的数据目录；已有凭据进入钥匙串，证书继续固定，不重新配对。
- 保留旧 LaunchAgent 的命令搜索路径，仅继承 `PATH`；后续手动保存连接设置不会清空它。
- 原生迁移放在后台执行；防止迁移中重复请求、启动执行器或退出应用；失败时尝试恢复旧服务并报告回退结果。

## 验证边界

迁移成功需要分别验证旧 LaunchAgent 停用、旧数据保留、新数据完整、随应用打包的 worker 接管，以及真实 QUIC 连接的证书、凭据和协议检查。仅弹窗显示成功或编译通过不代表完成迁移。

已通过 33 项前端测试、8 项原生测试、全部桌面 target 的 Clippy（警告视为错误）及 release `.app` 构建。原生测试包括旧格式任务迁入后同一编号返回 `duplicate` 且不执行、同步状态保留、源文件不变、安装失败回退、错误记录和未结束任务拒绝，以及 `PATH` 存储兼容。

本机安装包使用本地 ad-hoc 签名，严格签名校验通过；构建产物和安装副本的主程序哈希一致。这不是签名公证发布记录。真实连接信息、凭据、任务内容与迁移快照不进入仓库。

本轮实机切换开始前遇到 Mac 锁屏，界面工具明确要求用户手动解锁。因此实际迁移尚未执行，旧 LaunchAgent 保持运行；不能将上述自动化结果当成真实接管完成。
